# 开发规范与代码审计制度

## 1. 强制原则

所有代码变更必须经过 Pull Request / Merge Request 审核后才能合并。不得直接向受保护主分支推送业务变更，不得绕过审核。该规则适用于后端、前端、SDK、数据库迁移、部署配置、基础设施脚本、测试和安全策略代码。

## 2. 变更流程

1. 创建需求/缺陷任务并分配唯一编号。
2. 从主分支创建工作分支。
3. 开发并提交 Git Commit。
4. 创建 PR/MR，描述原因、范围、风险和验证方式。
5. 自动检查：格式、静态分析、测试、安全扫描、依赖检查及文档同步检查。
6. 人工审核；未通过不得合并。
7. 合并后记录发布版本、Commit、部署环境和回滚点。

## 3. 变更记录字段

- 变更编号
- 关联需求/缺陷编号
- 作者及时间
- 文件路径与新增/修改/删除类型
- Git Diff 与 Commit SHA
- 修改原因及影响范围
- 测试结果和检查报告
- 审核人及审核结论
- 发布版本及发布记录
- 回滚目标版本

每一行代码的变更都由 Git Diff 追踪；审计记录按 Commit/PR 组织，并能定位具体文件和行级差异。

## 4. 审核规则

- 所有代码 PR 必须至少经过人工审核。
- 提交者不得批准自己的 PR。
- 授权、签名、密钥、设备绑定、额度、余额和支付模块建议设置额外安全审核人。
- 未通过 CI 或存在未解决阻断级审查意见不得合并。
- 主分支保护、禁止强制推送和审核规则应在 GitHub 仓库设置中落实。
- 当前仓库权限允许管理并不等于保护规则已配置；配置状态需单独核验。

## 5. 禁止行为

- 生产服务器直接改代码。
- 未记录的文件覆盖或热修复。
- 未审核直接合并。
- 删除/篡改已归档审计记录。
- 将私钥、App Secret、支付密钥或生产凭据提交到 Git。
- 未经测试发布授权和财务核心逻辑。

紧急修复也必须补齐 PR、审核、测试和审计记录；紧急流程不能成为永久绕过机制。

## 6. 发布与回滚

每次发布必须绑定不可变 Commit SHA、版本号、构建产物摘要、测试结果、发布人、审批人和回滚版本。数据库迁移须提供前向/回滚策略及兼容性评估。发布过程应支持分批/灰度和故障回滚，具体策略另行设计。

## 7. 文档同步

API、数据库、授权协议、密钥、配置、SDK、部署或错误码变更必须检查相关文档。PR 模板应包含文档影响说明；适用时自动生成文档草稿并由人工审核。
## 8. 项目执行与交付责任

- 项目执行方负责按已确认需求持续推进开发、测试、缺陷修复、文档同步、PR 管理和交付，不因每个常规开发步骤反复要求需求方确认。
- 在需求边界已明确的范围内，执行方可自行创建分支、提交 PR、执行审核清单、修复问题并合并；涉及新增收费、不可逆数据删除、生产环境变更或改变已确认业务规则时，必须遵循相应审批和安全流程。
- 所有合并必须有可追溯 PR、完整 Diff、自动化检查结果和审查记录。不得伪造独立审核者身份或声称未实际执行的测试。
- 生产环境发布仍按已确认规则：测试环境自动部署，生产环境须由管理员批准。
- 完成交付时必须区分已实现、已测试、待部署、未验证和规划目标；不得将规划性能指标描述为已达标。
- 代码质量门禁：自动化测试、代码规范检查和安全扫描必须通过；阻断级问题未解决不得合并。
