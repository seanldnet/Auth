# 文档管理与自动生成规范

## 1. 目标

文档是项目交付物和版本基线。自动生成用于减少遗漏，人工审核用于确保业务语义、准确性和安全边界。未审核文档不得标记为正式发布。

## 2. 文档目录建议

- docs/requirements：PRD、需求变更和待确认事项。
- docs/architecture：总体架构、部署、容量、灾备。
- docs/security：威胁模型、密钥管理、安全基线。
- docs/protocol：授权协议、API、错误码和 SDK 接口。
- docs/data：数据模型、数据保留和日志。
- docs/development：开发规范、审计、文档治理。
- docs/operations：部署、监控、备份、故障处理。
- docs/testing：测试策略、性能验收和安全测试。

## 3. 自动生成范围

可从接口定义、代码注释/类型、数据库迁移、配置 schema、错误码定义、SDK 公共接口和 Git 变更记录生成文档草稿。自动生成内容必须标明生成来源和对应 Commit。

## 4. 审核状态

草稿 -> 自动生成待审核 -> 人工审核中 -> 已批准 -> 正式发布 -> 历史归档。

驳回文档须保留原因和修改记录。正式文档不能静默覆盖，更新必须产生新版本和差异记录。

## 5. 文档元数据

每份正式文档至少记录：文档编号、标题、版本、状态、负责人、创建时间、修改时间、审核人、审核时间、关联需求、关联代码 Commit、适用软件/平台版本。

## 6. 文档同步检查

PR 必须说明是否影响 API、数据库、SDK、配置、部署、安全或用户操作文档。若有影响，应更新文档或说明无需更新的理由。对自动生成文档，应保留生成输入和人工修改记录。

## 7. 文档安全

禁止在文档中放入真实私钥、App Secret、支付凭据、生产 Token 或用户敏感数据。示例必须使用虚构占位值。安全相关文档的访问范围和发布范围需按敏感等级控制。
## 8. 前端规范文档

前端页面布局、留白、组件间距、卡片 padding、表单密度和响应式验收以 `docs/development/frontend-ui-standards.md` 为准。页面开发 PR 必须按该文档逐项自检；不得以“功能可用”为由合并明显拥挤、内容贴边或无意义留白的页面。
