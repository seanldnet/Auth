# 全球架构设计（规划稿）

## 1. 架构目标

国内与海外各自部署独立授权验证集群，每个区域独立扩展至 80,000 QPS；规划流量比例为国内 50%、海外 50%。区域独立性是已确认要求；具体控制平面部署、数据同步范围和跨区域故障策略仍待确认。

## 2. 逻辑分层

1. 全球流量入口：DNS/全球流量调度、健康探测、DDoS 防护、区域路由。
2. 区域授权数据平面：无状态授权 API、区域缓存、区域数据库写入服务、消息队列、监控。
3. 管理控制平面：软件、用户、代理、授权、额度、财务、密钥、审计及文档管理。
4. 开发者接入层：统一协议、SDK、API 文档和版本兼容管理。

## 3. 区域独立性

国内、海外区域分别具备：
- 独立授权 API 节点池和负载均衡。
- 独立 Redis 集群及本地缓存。
- 独立数据库部署与备份策略。
- 独立消息队列、日志处理及监控告警。
- 独立扩容、故障隔离和容量规划。

不应把跨区域实时数据库调用放在每次授权验证的关键路径上。区域自治程度、权威数据归属和写入冲突解决规则须在数据一致性设计阶段确认。

## 4. 授权验证数据路径

建议路径：请求接入 -> 请求签名/时间戳/Nonce 校验 -> 软件身份和权限校验 -> 区域缓存读取 -> 必要时查询权威数据 -> 检查授权状态/期限/设备 -> 返回签名或结构化结果 -> 异步统计与审计。

缓存不能成为最终权威。冻结、作废、换机等高风险变更必须有版本号、缓存失效事件和失效确认机制。旧授权租约必须有明确上限，避免无限期接受过期状态。

## 5. 写入与一致性

激活、设备绑定、换机、额度扣减、余额变动等关键写入必须经过权威写入服务，并使用数据库事务、唯一约束、幂等键及业务状态机保护。不能只依赖 Redis 分布式锁保证正确性。

区域间事件应具备持久化、重试、幂等消费、死信处理、延迟监控和定期对账能力。跨区域网络分区时，高风险操作的允许/拒绝策略需明确，不能假设最终一致性自动满足安全要求。

## 6. 缓存与容量

规划 L1 进程内缓存 + L2 区域 Redis + L3 权威数据库。需要评估热点 Key、缓存击穿/雪崩、TTL 抖动、连接池、网络吞吐、Redis 分片及故障切换。缓存内容应带授权版本、密钥版本和过期时间。

## 7. 80,000 QPS 验收

国内和海外分别独立测试，不以全球总量平均值代替单区域指标。测试至少包括阶梯压测、目标负载长稳压测、峰值恢复、节点故障、缓存故障、数据库故障、消息队列积压、区域网络分区和缓存重建。

建议测试阶段覆盖 1k、5k、10k、30k、50k、80k QPS。P95/P99、错误率、持续时间、CPU/内存、网络带宽、数据库连接和缓存命中阈值须在性能验收计划中最终确认。

## 8. 可用性与灾备

规划要求覆盖节点摘除、自动扩容、区域健康检查、数据库备份恢复、消息重试、密钥备份恢复和灾难演练。99.99% 可用性、RPO、RTO 目前只是待决策指标，不能视为已承诺 SLA。

## 9. 数据合规

按用户所在司法辖区评估个人信息、设备标识、支付信息、数据驻留和跨境传输。区域独立部署不自动意味着可以自由复制全部数据；应明确数据分类、最小化同步、加密、访问审计和保留期限。
